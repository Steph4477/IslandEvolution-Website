# Mesure d’audience Umami V1.9

## Fonctionnement

La mesure est désactivée par défaut. `VITE_UMAMI_ENABLED=true` l’autorise dans le build destiné à `https://moko-islandevolution.com`. Sur ce domaine, le script officiel se charge uniquement après un accord Umami valide. Les choix sont intégrés au bas des pages, dans le flux du document. Après un choix, seul le bouton de préférences reste visible. La préférence est indépendante de YouTube. Le choix, accord ou refus, est valide jusqu’à 180 jours dans le navigateur. À l’échéance, le site cesse de l’utiliser, même si l’entrée reste dans le stockage local. Une préférence absente, expirée ou illisible interdit les envois. La clé de stockage est versionnée pour permettre un nouveau choix si la finalité change.

SvelteKit envoie manuellement une vue lors du premier affichage mesuré, puis une vue par changement de route. Le traceur utilise `data-auto-pageview="false"`. Les ancres et les paramètres de langue ne créent pas de vue supplémentaire. Le filtre `data-before-send` vérifie le consentement à chaque appel et autorise uniquement la charge préparée par le site. La lecture du choix stocké permet aussi de tenir compte d’un retrait effectué dans un autre onglet. Une requête lancée avant le retrait peut déjà avoir atteint le prestataire.

Pendant le chargement du traceur, une file d’attente en mémoire conserve jusqu’à 20 événements personnalisés, dans leur ordre d’arrivée et avec leur chemin d’origine. Chaque événement expire après 10 secondes au plus, ou à l’échéance du consentement si celle-ci arrive plus tôt. Lorsque la file est pleine, l’événement le plus ancien est écarté. Le retrait vide les événements de l’accord révoqué. Chaque nouvel accord enregistré reçoit un identifiant local distinct, enregistré avec le choix et jamais inclus dans les charges utiles. Les accords existants restent valides jusqu’à leur échéance ou à leur remplacement. Chaque événement en attente reste associé à l’accord qui l’a autorisé. Le choix et son identifiant sont revérifiés avant l’envoi, même si la notification `storage` d’un autre onglet n’est pas encore arrivée. Un échec de chargement ou une API indisponible vide la file. Une activation ultérieure peut relancer le chargement sans rejouer les événements supprimés. Les événements sont transmis directement lorsque le traceur est prêt. La file ne garantit aucune livraison lors de la fermeture de la page ou d’une navigation externe.

Le panneau relit le choix à l’ouverture et s’actualise lorsqu’il expire en restant ouvert, sans prolonger le choix ni envoyer d’événement. En cas d’échec d’écriture du refus, le site essaie de supprimer l’ancien choix. Si les deux opérations échouent, la collecte reste arrêtée dans l’onglet courant jusqu’à un nouveau choix explicite. Le panneau indique qu’un accord antérieur encore valide peut subsister dans un autre onglet ou après rechargement.

Le site envoie uniquement les chemins de routes connus et, pour la première vue, un domaine référent figurant dans une liste fixe. Les paramètres d’URL, les fragments, le chemin référent, les données de candidature et les identifiants personnalisés sont exclus. La mesure n’utilise ni les relectures de session ni la collecte automatique d’erreurs ou de performances. [Configuration du traceur](https://docs.umami.is/docs/tracker-configuration) · [Fonctions du traceur](https://docs.umami.is/docs/tracker-functions)

| Événement       | Action mesurée                                                                                                                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `beta_open`     | Ouverture effective de la modale de candidature.                                                                                                                                                        |
| `beta_mailto`   | Demande d’ouverture d’un brouillon après validation du formulaire. Les candidatures reçues et les inscriptions confirmées sont suivies manuellement.                                                    |
| `teaser_play`   | Lecture du teaser principal confirmée par le lecteur après activation du bouton de lecture du site. La lecture automatique et les commandes internes à l’iframe ne sont pas attribuées à cet événement. |
| `external_link` | Activation d’un lien social instrumenté, avec la catégorie fixe `social`. La catégorie `portfolio` est prévue si un lien de portfolio est ajouté.                                                       |

## Recette et activation

Pour la recette d’un build activé, définir `VITE_UMAMI_ENABLED=true` dans l’environnement du build et simuler le domaine public ainsi que le collecteur dans le navigateur de test. Vérifier sur PC et mobile les choix indépendants Umami et YouTube, le refus, le retrait après chargement du traceur, le retrait dans un autre onglet, les navigations FR/EN, les actions bêta et les charges utiles. Contrôler l’en-tête `Referer` aussi bien sur le script que sur la collecte. Sur le domaine public, vérifier également les directives `script-src` et `connect-src` si une CSP est servie. Utiliser la [procédure GitHub Pages](DEPLOIEMENT.md) pour la validation du build et pour toute publication autorisée.

Le 20 novembre 2026, la réponse HTTPS de l’accueil public était `200 OK` via GitHub Pages, sans en-tête `Referrer-Policy` ou `Content-Security-Policy`, ni balise méta équivalente. Le build V1.9 ajoute `strict-origin-when-cross-origin` au document et `no-referrer` au chargement du script. Le script public `https://cloud.umami.is/script.js` a répondu `200 OK` et utilise `https://gateway.umami.is/api/send`. Une requête CORS `OPTIONS` sans événement depuis l’origine MOKO a reçu `200 OK` avec le verbe `POST` et les en-têtes demandés autorisés. Si une CSP est introduite, vérifier séparément la source du script et la connexion à la passerelle.

La recette Chrome sur PC et à 390 px a exécuté cette copie du script officiel (SHA-256 `77c63c2d59d15b0ae0a694870804cd5d88ba2d0333d90ba1f3c81ff750aa90f3`). Les `POST` ont été interceptés dans le navigateur. Trois vues ont été observées pour le parcours accueil, confidentialité et retour. Les quatre événements attendus, le filtrage du référent et des paramètres, et l’absence de nouveaux envois après retrait ont été vérifiés. Ce contrôle porte sur les requêtes du navigateur. La réception et le stockage dans Umami Cloud restent à vérifier.

Pour vérifier le stockage réel, le propriétaire doit fournir le Website ID d’une propriété de recette distincte ou autoriser explicitement l’utilisation de la propriété existante pour des événements synthétiques. Le navigateur de recette peut servir le build local sur une origine MOKO interceptée et utiliser temporairement l’identifiant de recette dans ce seul profil. Le propriétaire vérifie ensuite dans le tableau de bord de la propriété les vues et événements reçus pendant le créneau indiqué. Une publication du site ou un partage de mot de passe ou de clé API n’est pas nécessaire pour ce contrôle.
